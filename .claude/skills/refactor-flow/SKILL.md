# RBE 리팩토링 플로우

인자: 대상 도메인 (예: `encoder`, `decoder`, `nlp::linear`). 없으면 사용자에게 확인.

## 절차 (순서 엄수)

### 1. 기준선 확보

test-runner 에이전트로 대상 도메인의 테스트를 먼저 실행하여 현재 통과 상태와 성능 수치를 기록한다. 이미 실패하는 테스트가 있으면 리팩토링을 시작하지 말고 사용자에게 보고한다.

### 2. 개선점 파악

우선순위: 중복 코드 제거 > 복잡한 조건문 단순화 > 긴 함수 분리 > 네이밍 개선 > 불필요한 주석 제거 > 포맷팅.

제약:
- 로직(수치 결과)을 바꾸지 않는다. 리팩토링 전후 출력이 비트 단위로 달라질 수 있는 변경(연산 순서 변경, f32/f64 변경 등)은 리팩토링이 아니라 로직 변경이므로 별도 승인 필요
- 기존 public 함수 이름을 불필요하게 바꾸지 않는다
- 유사 로직의 새 파일을 만들지 않는다. 기존 파일을 수정한다

### 3. 리팩토링 실행

작은 단위로 수정하고 각 단위마다 `cargo check`로 컴파일을 확인한다.

### 4. 테스트 재실행

test-runner 에이전트로 동일 도메인 테스트를 재실행한다. 전부 통과해야 한다. 실패 시:
- 허용 오차나 기대값을 수정해서 통과시키는 것은 절대 금지 (테스트 수치 변경은 사용자 승인 사항)
- 리팩토링 코드를 수정해서 통과시키거나, 원인을 보고하고 지시를 기다린다

### 5. 정합성 확인

수식·비트 구조를 건드린 경우 paper-checker 에이전트로 docs/paper 문서와 정합성을 확인한다.

### 6. 사용자 컨펌 대기

변경 요약과 테스트 결과를 보고하고 컨펌을 받는다.

### 7. 성능 보고서

컨펌 후 perf-reporter 에이전트로 `docs/test/<도메인>.md` 성능 보고서를 작성·갱신한다.
